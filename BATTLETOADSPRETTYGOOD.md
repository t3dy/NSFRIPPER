# Battletoads: How We Got to "Pretty Good"

## The Journey

### Where We Started (Sessions 1-3)

We had a working Rare driver parser (39 commands, 4 channels, zero parse
errors) and a frame simulator — but the output sounded wrong. The previous
sessions identified a "period transform gap" where the parser computed
periods up to 1524 (D2) but the Mesen trace never exceeded 961 (A#2).

Three sessions were spent trying to explain this gap: disassembling the
note handler, checking hardware sweep registers, modeling arpeggio and
vibrato systems, investigating bank switching. The parser kept getting
more sophisticated but the output kept not matching the game.

### The Breakthrough (This Session)

The entire problem was **wrong song identification.**

The NSF init routine at $8054 has a lookup table at $8060 that maps NSF
song indices to internal IDs:

```
NSF Song 1 (idx 0) → internal ID 16  (title screen)
NSF Song 2 (idx 1) → internal ID 3   (Level 1 — Ragnoraks Canyon)
NSF Song 3 (idx 2) → internal ID 4   (different arrangement)
```

We had been using NSF Song 3 / internal ID 4. Level 1 is Song 2 / ID 3.
The parser was pointed at $A2CF (ID 4's P2 data). The actual Level 1 P2
data is at $AC94 (ID 3).

The Mesen trace was always correct — it captured actual Level 1 gameplay.
The "period gap" was us comparing Level 1 trace data against a different
song's ROM data. There was never a transform gap. We were looking at
different music.

### How I Found It

1. Extracted P2 periods from the NSF SysEx data for Song 3. They went up
   to 1526 — matching the parser exactly. This proved the parser was
   correct for Song 3, but raised the question: why doesn't the trace
   match Song 3?

2. Compared NSF Song 2 vs Song 3 note distributions against the fan MIDI
   reference (`battletoads_level1.mid`):

   | Channel | Fan MIDI | Song 2 | Song 3 |
   |---------|----------|--------|--------|
   | P1 | E4, B4, D5 | E4, B4, D5 | D2, A1, G1 |
   | P2 | E2, D2, B2 | E2, D2, B2 | A2, D3, G2 |

   Song 2 matched. Song 3 didn't.

3. Confirmed with librosa pitch analysis of the Song 2 MP3: dominant
   pitches E2, G2, B2, E4 — the Level 1 riff.

### The Weird High Note Fix

The "too high note at the end of the eight-note sequence" was the wrong
song's melody bleeding through. Song 3 has high-octave notes (G6 sweep
notes, C6, G5) that Song 2 doesn't. When we switched to Song 2, those
artifacts disappeared because we were finally playing the right music.

### The Stale MIDI Problem

An additional issue: the old `Battletoads_02_Song_2_v1.mid` on disk had
P2 an octave too low (E1 instead of E2). This was generated by a previous
version of the extraction code. Re-running the extraction with the current
`nsf_to_reaper.py` produced correct MIDI 40 (E2) from period 1358.

Verified by running `period_to_midi(1358, is_tri=False)` = 40 (E2).
The old file had `period_to_midi(1358, is_tri=True)` = 28 (E1) — the
triangle octave correction was being applied to a pulse channel.

### The Tempo Correction

Previous sessions reported Level 1 tempo as 130 (0x82). The actual value
from $959E[4] is 87 (0x57). However, that's for internal ID 4. Internal
ID 3 (actual Level 1) uses $959E[3] = 122 (0x7A). This changes the
frame-per-tick ratio and will matter for the parser/simulator once they
are pointed at the correct song addresses.

## What We Have Now

### Production Output

```
output/Battletoads_Level1/
  midi/Battletoads_02_Song_2_v1.mid     # 432+368+178+116 notes, SysEx Track 5
  reaper/Battletoads_02_Song_2_v1.rpp   # Console route (CC playback)
  reaper/Battletoads_02_Ragnoraks_Canyon_APU2_v1.rpp  # APU2 route (SysEx replay)
  wav/Battletoads_02_Song_2_v1.wav      # Pre-rendered audio
```

### Quality

- P1 (lead): 432 notes, 1664 CC11 events — E4/B4/D5 melody, correct octave
- P2 (bass): 368 notes, 2185 CC11 events — E2/D2/B2 riff, correct octave
- Triangle: 178 notes — A2/E2/B2 bass support
- Noise: 116 drum hits — F#2/C2/D2 pattern
- All pitches verified against fan MIDI reference
- User ear-check: "pretty good"

### What's Still Hypothesis

The ROM parser (39 commands, zero parse errors) is structurally correct
but was parsing the WRONG SONG (internal ID 4, not ID 3). It has not
been re-pointed to the correct Level 1 addresses. Parser output for
Level 1 is therefore untested.

## Timeline of Mistakes

| Session | Mistake | Cost | Root Cause |
|---------|---------|------|------------|
| 1-2 | Assumed NSF Song 3 = Level 1 | ~10 prompts | Didn't verify against reference audio |
| 2-3 | Investigated "period gap" for 3 sessions | ~20 prompts | The gap was comparing two different songs |
| 3 | Reported tempo as 130 | 2 prompts | Read $959E[4] for ID 4, not ID 3 |
| 4 | Generated RPPs from Song 3, told user to test | 3 prompts | Same song misidentification |
| 4 | Declared "NSF is authority, trace is wrong" | 2 prompts | Violated CLAUDE.md: Mesen wins |
| 4 | Found stale MIDI with octave error | 1 prompt | Old extraction on disk, not regenerated |

Total cost of the song misidentification: **~35 prompts across 4 sessions.**

## What Actually Solved It

1. **Comparing against the MP3 reference** — pitch analysis of the MP3
   immediately showed the output was wrong
2. **Checking ALL NSF songs** against the fan MIDI signature, not just
   the one we assumed was correct
3. **Re-extracting from scratch** instead of trusting old files on disk

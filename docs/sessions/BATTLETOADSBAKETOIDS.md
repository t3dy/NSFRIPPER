# Battletoads: Bake These Into the System

Lessons from the Battletoads extraction that should change how we work.

## 1. Song Verification Gate (MANDATORY)

### The Problem

We spent 4 sessions parsing the wrong song. The NSF song-to-internal-ID
mapping was assumed, never verified against audio. This single mistake
cost ~35 prompts.

### The Fix

Before any extraction work on a new game, run a **song verification gate**:

```bash
# Step 1: Extract all songs from NSF
python scripts/nsf_to_reaper.py <nsf> --all -o output/<Game>/

# Step 2: Generate MP3s for all songs
# (already happens in the pipeline)

# Step 3: Identify which song matches the target
python scripts/identify_song.py <game> --reference <fan_midi_or_mp3>
```

`identify_song.py` doesn't exist yet. It should:
1. Load reference audio (fan MIDI, MP3, or YouTube rip)
2. Extract pitch distribution from reference
3. Compare against each NSF song's pitch distribution
4. Report the best match with confidence score
5. Block extraction work until match is confirmed

**This is a 50-line script that would have saved 35 prompts.**

### Where to Bake It

- `session_protocol.md` — add as Gate 0 before any extraction
- `CLAUDE_EXTRACTION.md` — add to per-game checklist as step 0
- `kitchen_sink.py` — add `--verify-song` flag

## 2. Always Compare Against Reference Audio

### The Problem

We trusted the parser, the trace, the ROM disassembly — everything
except actually listening to whether it sounds like the game. When
the user said "this sounds nothing like Level 1," that was more
informative than 20 prompts of 6502 analysis.

### The Fix

Add a reference comparison step to every extraction:

```python
# In session_startup_check.py or kitchen_sink.py
def verify_against_reference(midi_path, reference_path):
    """Compare MIDI pitch distribution against reference audio."""
    # Extract top-5 notes from both
    # Flag if dominant notes don't match
    # Return pass/fail with details
```

The MP3 files from `nsf_to_reaper.py --all` are already generated. Use
them as reference. Librosa pitch extraction takes 5 seconds and catches
wrong-song errors immediately.

### Where to Bake It

- `session_protocol.md` delivery gate — "reference audio compared"
- `synth_fidelity.md` — add reference comparison as fidelity check

## 3. Don't Trust Files on Disk

### The Problem

`Battletoads_02_Song_2_v1.mid` on disk had P2 an octave low. It was
generated by an older version of the code. We trusted it and wasted
time debugging a non-issue.

### The Fix

When investigating a problem, **always regenerate from source** before
analyzing. Old MIDI files, old RPPs, old WAVs may reflect bugs that
have since been fixed.

Add to `session_protocol.md`:
```
Before debugging output quality:
1. Regenerate MIDI from NSF/trace (don't trust files on disk)
2. Regenerate RPP from fresh MIDI
3. THEN compare/debug
```

## 4. NSF Song Number != Internal Song ID

### The Problem

We assumed NSF Song N = internal ID N. It doesn't. NSF files have a
patched init routine with a lookup table that remaps song indices.

### The Fix

For every NSF, decode the init routine's song mapping table:

```python
def decode_nsf_song_map(nsf_path):
    """Extract the NSF song index -> internal ID mapping."""
    with open(nsf_path, 'rb') as f:
        data = f.read()
    init_addr = data[10] | (data[11] << 8)
    load_addr = data[8] | (data[9] << 8)
```

This should be part of `rom_identify.py` output and stored in the manifest.

- `extraction/manifests/*.json` — add `nsf_song_map` field
- `rom_identify.py` — decode and display the mapping
- `CLAUDE_EXTRACTION.md` checklist — "verify NSF song mapping"

## 5. Simplify the Pipeline

### Current State

We have too many extraction routes that can get confused:

- NSF → py65 emulation → per-frame capture → MIDI
- ROM → parser → simulator → Frame IR → MIDI
- Mesen trace → trace_to_midi → MIDI
- kitchen_sink.py tries to run all routes and compare

### Recommendation: Two Routes, Not Four

**Route A: NSF (standard, default for all games)**
```
NSF → nsf_to_reaper.py → MIDI + SysEx + RPP
```
This already works for Battletoads Level 1. 432+368+178+116 notes,
correct pitches, per-frame CC11 envelopes, SysEx for APU2 replay.
It's the 6502 CPU running the actual driver code. For most games,
this is sufficient and correct.

**Route B: Trace (only when NSF diverges from gameplay)**
```
Mesen capture → trace_to_midi.py → MIDI + RPP
```
Only needed when the NSF and actual game audio differ (proven for
Mario, suspected for some Battletoads tracks). The trace captures
what the real hardware does during gameplay.

**Kill Route C (ROM parser → simulator → Frame IR)**

The ROM parser was a 4-session investment that parsed the wrong song.
The parser IS valuable for understanding driver architecture, but as
a production extraction route it adds complexity without adding quality
over the NSF route. The NSF runs the same 6502 code as the parser
tries to simulate — but the NSF does it correctly by definition.

The parser should be reclassified as a **research/analysis tool**, not
a production pipeline stage. Use it to:
- Understand driver command formats
- Decode song structure (subroutines, loops, transpositions)
- Generate documentation
- Investigate NSF/trace discrepancies

Don't use it to generate MIDI. The NSF already does that better.

### Recommendation: Simplify kitchen_sink.py

Currently tries to run all routes. Should instead:
1. Run NSF route (always)
2. Run trace route (if capture exists)
3. Compare NSF vs trace (flag divergences)
4. Compare against reference audio (flag wrong songs)
5. Pick the best route automatically

## 6. Synth Improvements

### What Works

The Console synth plays back CC11/CC12 envelopes correctly. The APU2
synth replays SysEx registers for hardware accuracy. Both produce
recognizable Battletoads music.

### What Could Be Better

**Per-game presets.** Battletoads uses specific duty cycle patterns and
envelope shapes that differ from Castlevania/Contra. The synth should
have a "Battletoads" preset that configures:
- Default duty cycle (the Rare driver's characteristic sound)
- ADSR shape for keyboard play that mimics the Rare envelope
- Noise channel mapping for the continuous hi-hat pattern

**Noise channel rendering.** Battletoads noise is unusual — constant
vol=5 with subtle bumps to vol=6 as "hits." The standard drum
detection (volume spike = hit) doesn't capture this well. The NSF
extraction got 116 hits, which is decent, but the actual pattern
is a continuous textured noise with rhythmic accents.

### What to Build Next for Synth

1. Nothing. The synth works. Focus on content (more games, more songs).
2. If the user wants video recording: ensure the Console UI knobs
   animate during Battletoads playback for visual interest.
3. If keyboard play is wanted: create a Battletoads ADSR preset that
   captures the characteristic Rare sound (bright attack, quick decay).

## 7. Per-Game Extraction Checklist (Updated)

```
[ ] 0. SONG VERIFICATION: identify correct NSF song against reference
[ ] 1. Extract NSF for target song(s)
[ ] 2. Verify pitches against fan MIDI / MP3 / game audio
[ ] 3. Check note counts are reasonable (not 1 note for noise, etc.)
[ ] 4. Generate RPP (Console route)
[ ] 5. Ear-check in REAPER against game
[ ] 6. If NSF sounds wrong: capture Mesen trace, use trace route
[ ] 7. If trace also sounds wrong: THEN investigate with ROM parser
[ ] 8. Version output files, never overwrite
```

## Summary

The single most impactful improvement to the pipeline is a **song
verification gate** — a quick pitch-distribution comparison against
reference audio before any extraction work begins. This catches
wrong-song errors in seconds instead of sessions.

The second most impactful improvement is **trusting the NSF route as
default** and only falling back to trace/parser when the NSF provably
diverges from gameplay. The NSF runs the real driver code. Duplicating
that logic in a Python parser adds risk without adding fidelity.
